# 贡献指南 / Contributing

感谢你帮助维护 Awesome DSH Plugin。

Thank you for helping maintain Awesome DSH Plugin.

## 收录标准 / Inclusion criteria

- 仓库必须公开，并带有 `dsh-plugin` GitHub Topic。
- 仓库必须填写 GitHub 项目简介（description）；没有简介的仓库不予收录，补充简介后会进入[待审核队列](./data/review/pending.md)，经维护者核实后加入。
- 仓库本身必须是可安装的 DSH 插件（或明确的 DSH 生态资源），而不是另一个插件目录/榜单站点，也不是蹭 `dsh-plugin` Topic 的其他 Agent 工具或无关项目（即使带了 `dsh-plugin` Topic）。明显不符合的仓库可以登记在 `data/curated.json` 的 `excluded_repos` 中并注明原因。
- 项目说明应准确、简洁，不使用无法核实的宣传语。
- 请披露归档、许可证缺失或明显安全风险等重要状态。
- A repository must be public and carry the `dsh-plugin` GitHub topic.
- A repository must have a GitHub description set; repositories without one are excluded until a description is added, then enter the [review queue](./data/review/pending.md) and are included after the maintainer verifies them.
- The repository must be an installable DSH plugin itself (or a clear DSH ecosystem resource), not another plugin directory/leaderboard site, and not another agent tool or unrelated project riding the `dsh-plugin` topic for reach. Clear mismatches can be listed with a reason in `excluded_repos` in `data/curated.json`.
- Descriptions should be accurate and concise, without unverifiable marketing claims.
- Important status such as archival, missing license, or evident security risk should be disclosed.

## 作者自荐 / Self-promotion

「作者自荐」区是插件作者自行提交的推荐位：**不经编辑部审核**，但仍须满足上方收录标准。完整列表在 [SHOWCASE.md](./SHOWCASE.md)（最多 30 条），两个 README 首页只展示**最近 10 条**预览。规则：

- 仅限仓库作者或维护者本人提交；一个 PR 只推荐一个仓库。
- PR 描述中必须附**自荐说明**：解决什么问题、适合谁（一两句即可，中文或英文任一；不使用无法核实的宣传语）。
- 仓库须满足上方收录标准（公开、带 `dsh-plugin` Topic、已填写简介、是真实的 DSH 插件或生态资源）。
- 自荐仓库的 Star 数必须**超过 10 个**（`stargazers_count > 10`）；Star 数不足的仓库暂不收录，请先在社区积累后重新提交。CI 会在每个 PR 上自动核验，不达标的 PR 将被拒绝。
- PR 标题必须为正常编码的 UTF-8 文本；出现乱码（如 `????`）的标题一律拒绝。
- 改动方式：在 [SHOWCASE.md](./SHOWCASE.md) 的「作者自荐」与「Author showcase」两个列表**末尾各追加一行**（中英对应）即可；若列表已有 30 条，同时移除最旧的一条（先进先出）。**两个 README 首页的自荐预览区由脚本自动生成，请不要手工同步、也不要编辑**（区域由 `<!-- dsh:showcase:start/end -->` 标记界定）——SHOWCASE.md 变更合入 main 后，`refresh-showcase` 工作流会立即刷新预览（本地可跑 `node scripts/showcase-preview.mjs`），审核合并时 `scripts/merge.mjs` 也会一并生成。不要改动其他人工维护内容，也不要提交生成文件。
- 自荐区最多保留 30 条，区满后先进先出；条目被首页精选推荐收录后会从自荐区移除、不占名额。
- 提交前本地自检：`node scripts/validate-curated.mjs`（会校验 SHOWCASE.md 与两个 README 自荐区格式和同步关系，并通过 GitHub API 确认仓库公开且带 Topic；无 token 或 API 限流时可用 `--from-snapshot` 改用本地快照校验）。PR 上的 CI 还会自动核验**标题编码**与**自荐仓库的 Star 数（>10）**，请提交前自查。自荐预览区**滞后**于 SHOWCASE.md 属预期状态（合入后由 `refresh-showcase` 工作流刷新），本地与 PR 校验只提示警告、不会失败；仅当预览与 SHOWCASE.md 的任何连续片段都对不上（手改/漂移）时才报错。

The Author showcase is a self-submission lane for plugin owners: **no editorial review**, but the inclusion criteria above still apply. The complete list lives in [SHOWCASE.md](./SHOWCASE.md) (at most 30 entries); the two README home pages show only a preview of the **10 most recent** entries.

- Only the repository owner or a maintainer may submit; one repository per pull request.
- The PR description must include a short **self-recommendation**: what problem it solves and for whom (one or two sentences, Chinese or English; no unverifiable marketing claims).
- The repository must meet the inclusion criteria above (public, `dsh-plugin` topic, description set, a real DSH plugin or ecosystem resource).
- The self-promoted repository must have **more than 10 stars** (`stargazers_count > 10`); repositories below the threshold are not listed — resubmit after the community has grown. CI verifies this on every PR and rejects submissions that fall short.
- The PR title must be properly encoded UTF-8 text; garbled titles (e.g. `????`) are rejected outright.
- How to change it: append exactly one line to the end of both the "作者自荐" and "Author showcase" lists in [SHOWCASE.md](./SHOWCASE.md) (Chinese and English), and drop the oldest entry when the list already holds 30 (first in, first out). **The home-page showcase previews are generated by scripts — do not sync or edit them by hand** (the region is delimited by `<!-- dsh:showcase:start/end -->`): once your SHOWCASE.md change lands on main, the `refresh-showcase` workflow refreshes the previews immediately (locally: `node scripts/showcase-preview.mjs`), and `scripts/merge.mjs` regenerates them at review-merge time too. Do not touch other hand-maintained content or commit generated files.
- At most 30 entries are kept — first in, first out; entries promoted to the home page's featured picks are removed from the showcase without using a slot.
- Validate locally before submitting: `node scripts/validate-curated.mjs` (it checks the SHOWCASE.md and README showcase sections for format and sync, and confirms repositories are public and carry the topic through the GitHub API; without a token or under API rate limits, add `--from-snapshot` to validate references against the stored snapshot instead). CI on the PR additionally verifies the **title encoding** and the **self-promoted repository's star count (>10)** — check both before you submit. A showcase preview that **lags** SHOWCASE.md is the expected pre-merge state (the `refresh-showcase` workflow refreshes it right after merge) — local and PR validation only warn about it; validation fails only when the preview matches no contiguous stretch of SHOWCASE.md (a hand edit or drift).

## 挑战首页精选 / Challenging a featured pick

「作者自荐」不审核、挂上即展示；首页[精选推荐](./README.md#-精选推荐)的各场景行与[新手入门组合](./README.md#-新手入门组合)则是编辑部维护的推荐位——但可以**通过 PR 挑战**：提交一份具体的对比报告，如果你的插件比在位者更适合那个场景，或者补上了首页尚未覆盖的盲区，就能替换或新增。与自荐不同，本通道**经编辑部审核**。规则：

- 仅限仓库作者或维护者本人提交，仓库须满足上方收录标准；一个 PR 只挑战一个位置（一行有多个插件时，指明要替换哪一个）。
- **硬性门槛**：自首个公开发布版本起持续维护超过 2 个月——版本分布在整段期间而非一次性堆出，且提交时仍在维护；已停更或已归档的仓库不符合。公开发布版本不少于 10 个（GitHub Releases、npm 版本或等价可公开核验的发布记录）。
- **替换在榜条目**：PR 描述必须附一份**具体对比报告**，至少包含：① 目标位置（哪个分组、哪一行的哪个插件）；② 门槛自证——首个发布版本日期、版本列表（releases / npm 页链接）与近期维护记录；③ 逐项对比——功能覆盖、文档与上手成本、维护活跃度、安装方式与宿主兼容性、实测体验，每一项都附可核验证据（releases、提交记录、截图或录屏链接）；④ 如实写出在位插件的优势与你的插件仍不如它的地方——一边倒、只挑对方毛病的报告视为不公允，直接拒绝。对比足够说服人时新条目替换旧条目：被替换的仓库只是让出首页推荐位，仍保留在全量目录、榜单与原在的提交区，**不要在同一个 PR 里顺手移除它**。
- **Agent 公平复核**：提交即视为知情——维护者会在本地把对比报告（补盲则为场景论证）交给 Agent 独立复核：核验硬性门槛（版本数、维护期）与证据链接真伪，站在在位插件一侧重新评估结论是否公允，补盲场景还会核对它是否确为首页空白。夸大其词、隐瞒对方优势或无法核验的声明都会被复核抓出；复核意见连同审核结论公开在 PR 中。
- **补盲区**：首页尚未覆盖的场景可以新增一行——套用现有「想……」句式写清解决什么问题、适合谁，并说明与相邻条目为何不是一回事；入门组合同理，新增或替换套装行都要说清适合谁、为什么是更合理的组合。
- **改动方式**：直接编辑 [README.md](./README.md) 与 [README_EN.md](./README_EN.md) 的对应分组（首页内容必须中英同步）；新条目有截图的，可同时补进该分组下方的三联截图表（用仓库内可公开访问的图片直链）。不要改动 `<!-- dsh:... -->` 标记内的生成区。
- 审核通过并合入后，若该条目原在自荐区，会按惯例从 [SHOWCASE.md](./SHOWCASE.md) 移出、不占自荐名额。

Unlike the unreviewed Author showcase, the scenario rows under [Featured picks](./README_EN.md#-featured-picks) and the [Starter kits](./README_EN.md#-starter-kits) combos are editorially maintained slots — but you can **challenge them with a pull request**: submit a concrete comparison report — if your plugin fits a scenario better than the incumbent, or fills a gap the home page misses, it can replace or join the list. This lane **is editorially reviewed**. Rules:

- Only the repository owner or a maintainer may submit, and the repository must meet the inclusion criteria above; one pull request challenges one slot (when a row lists several plugins, name the one you are replacing).
- **Hard requirements**: continuously maintained for over 2 months since the first public release — versions spread across that whole period rather than dumped at once, and still maintained at submission time; abandoned or archived repositories do not qualify. At least 10 public releases (GitHub Releases, npm versions, or equivalently verifiable release records).
- **Replacing an incumbent**: the PR description must carry a **concrete comparison report** containing at least: (1) the target — which group, which row, which plugin you replace; (2) threshold evidence — the first release date, the release list (releases / npm page links), and recent maintenance history; (3) a point-by-point comparison — feature coverage, documentation and onboarding cost, maintenance activity, install method and host compatibility, hands-on behavior — each item backed by verifiable evidence (releases, commit history, screenshots or recordings); (4) an honest account of the incumbent's strengths and where your plugin still falls short — a one-sided report that only lists the other's faults counts as unfair and is rejected on sight. When the comparison is convincing, the new entry replaces the old: the replaced repository only yields the front-page slot — it stays in the full catalog, the leaderboard, and wherever it was submitted, so **do not remove it elsewhere in the same PR**.
- **Agent fair re-review**: submitting means you accept this — the maintainer runs an Agent locally to independently re-review your comparison report (or, for gap-fills, the gap rationale): it verifies the hard requirements (release count, maintenance window) and the authenticity of evidence links, re-evaluates your conclusion from the incumbent's side, and for gap-fills checks that the gap is real. Exaggeration, hidden rival strengths, or unverifiable claims are caught; the findings are posted on the PR together with the editorial decision.
- **Filling a gap**: a scenario the home page does not yet cover can be added as a new row — reuse the "I want…" phrasing to state the problem and the audience, and explain why it is not the same thing as its neighbors; the same applies to starter kits — a new or replacement combo must say who it is for and why it is the better combination.
- **How to edit**: edit the matching group in [README.md](./README.md) and [README_EN.md](./README_EN.md) directly (home-page content must stay bilingual); if the new entry has a screenshot, you may add it to the three-column screenshot table under that group (use a publicly reachable image URL inside the repository). Do not touch the generated regions inside `<!-- dsh:... -->` markers.
- Once approved and merged, an entry that was in the Author showcase is removed from [SHOWCASE.md](./SHOWCASE.md) as usual and no longer uses a showcase slot.

## 推荐一个插件 / Recommending a plugin

首页的精选推荐（场景分组）、入门组合、最近加入（[README.md](./README.md) / [README_EN.md](./README_EN.md)）和 [SHOWCASE.md](./SHOWCASE.md) 都是人工维护页面（首页的生态全景、热度榜 Top 50 与自荐预览三个区块由 `scripts/merge.mjs` 生成，勿手工编辑）：直接编辑对应 Markdown，并附上清晰的使用场景和理由（首页内容请同时提供中英文）。热度榜 [TOP200.md](./TOP200.md) 由 `scripts/top.mjs` 从快照生成、[CATALOG.md](./CATALOG.md) 与 `catalog/` 下的各分类分册由 `scripts/merge.mjs` 生成，两者都受 [data/approved.json](./data/approved.json) 门控（新仓库经核实后才出现），不要直接编辑；要把某仓库排除出榜单，请登记到 `data/curated.json` 的 `leaderboard_exclusions`（保留在目录、但不参与榜单排序）。分类覆盖、蹭 Topic 排除名单与榜单排除也写在 `data/curated.json`。

The home-page featured picks, starter kits, recently-joined sections ([README.md](./README.md) / [README_EN.md](./README_EN.md)), and [SHOWCASE.md](./SHOWCASE.md) are hand-maintained pages (the ecosystem mindmap, the Top 50 leaderboard, and the showcase preview are generated by `scripts/merge.mjs` — do not edit them by hand): edit the corresponding Markdown directly and include a clear use case and rationale (bilingual wording for the home pages). The leaderboard [TOP200.md](./TOP200.md) is generated by `scripts/top.mjs` from the snapshot and [CATALOG.md](./CATALOG.md) plus the per-category volumes under `catalog/` by `scripts/merge.mjs`; both are gated by [data/approved.json](./data/approved.json) (new repositories appear only after verification) — do not edit them directly. To keep a repository out of the board, register it under `leaderboard_exclusions` in `data/curated.json` (it stays in the catalog but does not rank). Category overrides, the topic-rider exclusion list, and board exclusions live in `data/curated.json`.

**PR 里的生成文件分两类处理。** `CATALOG.md`（目录索引）、`catalog/*.md`（各分类分册）、`TOP200.md` 是**目录页**：只改人工页面（README、SHOWCASE.md 等）的 PR 不要附带它们；但改动 `data/approved.json` / `data/curated.json` 且会影响目录归属的 PR（例如新增分类覆盖或排除）**必须**附上 `node scripts/merge.mjs` 重新生成的目录页——CI 会用 `merge.mjs --check` 核对「哪个仓库在哪一册」，只比对归属，不比对每日变动的星数和日期，所以 PR 跨过每日快照也不会误报。`merge.mjs` 同时会改写 `data/review/pending.*`，提交前请用 `git checkout origin/main -- data/review` 还原。市场 feed（`market-catalog.json` / `packages.json`）由 `publish-npm-feed` 工作流在发布时生成，不提交到仓库，PR 不要附带；`data/repositories.json` 与 `data/review/pending.*` 是每日流水线文件，一律不接受。PR 的 CI 会做**路径白名单**校验：只允许 SHOWCASE.md、README.md / README_EN.md、`data/curated.json`、`data/approved.json`、`data/packages.json`、`data/leaderboard-descriptions-zh.json`、`scripts/`、`.github/` 与仓库元文件，外加上述规则内的生成文件（改动 `scripts/` 的 PR 可附带任何生成文件，用于展示脚本输出变化）；其余路径（如自创的 `data/plugins/*.yml`）会被直接拒绝——那不是本仓库的提交通道。维护者可给 PR 打 `ci: allow-any-path` 标签跳过路径检查（打标签会自动重跑校验）。

**Generated files in pull requests come in two kinds.** `CATALOG.md` (the index), `catalog/*.md` (the per-category volumes), and `TOP200.md` are **catalog pages**: a PR that only touches hand-maintained pages (README, SHOWCASE.md, …) must not include them, but a PR that changes `data/approved.json` / `data/curated.json` in a way that moves catalog membership (a new category override or exclusion, say) **must** include the pages regenerated by `node scripts/merge.mjs` — CI checks "which repository sits in which volume" with `merge.mjs --check`, comparing membership only, not the star counts and dates the daily snapshot moves, so a PR that stays open across a snapshot refresh does not fail spuriously. `merge.mjs` also rewrites `data/review/pending.*`; restore those with `git checkout origin/main -- data/review` before committing. The market feed (`market-catalog.json` / `packages.json`) is generated at release time by `publish-npm-feed` and never committed — leave it out of PRs; `data/repositories.json` and `data/review/pending.*` are daily-pipeline files and are never accepted. The PR CI enforces a **path whitelist**: only SHOWCASE.md, README.md / README_EN.md, `data/curated.json`, `data/approved.json`, `data/packages.json`, `data/leaderboard-descriptions-zh.json`, `scripts/`, `.github/`, and repo meta files are accepted, plus generated files under the rules above (a PR that changes `scripts/` may include any generated file to show how the output changes); any other path (e.g. a made-up `data/plugins/*.yml`) is rejected outright — that is not a submission lane in this repository. Maintainers may label a PR `ci: allow-any-path` to skip the path check (labeling re-runs the check automatically).

提交前本地自检 / Check your change locally before submitting:

```bash
node scripts/validate-curated.mjs
```

它会校验分类名和 `owner/repo` 引用格式，并通过 GitHub API 确认分类覆盖引用的仓库公开存在且带有 `dsh-plugin` Topic。同样的检查会在 PR 上自动运行。

It validates category names and `owner/repo` reference formats, and confirms through the GitHub API that category-override repositories are public and carry the `dsh-plugin` topic. The same check runs automatically on pull requests.

## 更新数据 / Refreshing data

流水线分为两段，约定见 [data/review/README.md](./data/review/README.md)：

1. **脚本只抓原始数据。** 每日 `update-catalog` 工作流运行 `scripts/update.mjs`：刷新 `data/repositories.json` 快照与待审核队列 `data/review/pending.*`。它不生成 `CATALOG.md`、`catalog/` 分册、`TOP200.md`——新仓库在人工核实前不会出现在任何用户可见页面。

```bash
node scripts/update.mjs                 # 从 GitHub 刷新快照 + 待审核队列（需 GITHUB_TOKEN）
node scripts/update.mjs --from-snapshot # 仅用现有快照刷新待审核队列
```

2. **审核后合并。** 维护者审阅 `data/review/pending.md`（**先看「Star 异常增长」告警节**：一天内 +100★ 或突然窜上榜单的仓库要做增强分析，热度并非来自 DSH 插件本身时写入 `leaderboard_exclusions`），把决定记入 `data/approved.json`（通过）与 `data/curated.json`（剔除 / 不进榜单），然后运行：

```bash
node scripts/merge.mjs   # 重新生成 CATALOG.md、catalog/ 分册、TOP200.md 与待审核队列
node scripts/top.mjs     # 单独重新生成 TOP200.md（同样受 approved 门控）
```

原始快照保留 Topic 下的全部仓库（含未填简介和已列入排除名单的条目），过滤与门控只发生在目录页与榜单页渲染阶段，便于人工分析时看到完整数据。刚创建的仓库会晚于 `data/repositories.json` 快照，因此 `--from-snapshot` 重建的队列看不到它；这属于正常现象，用完整的 `node scripts/update.mjs` 验证即可。

The pipeline has two stages — see [data/review/README.md](./data/review/README.md) for the convention:

1. **Scripts only fetch raw data.** The daily `update-catalog` workflow runs `scripts/update.mjs`: it refreshes the `data/repositories.json` snapshot and the review queue `data/review/pending.*`. It does not generate `CATALOG.md` or `TOP200.md` — a new repository never appears on a user-facing page before a human has verified it.

```bash
node scripts/update.mjs                 # refresh snapshot + review queue from GitHub (needs GITHUB_TOKEN)
node scripts/update.mjs --from-snapshot # refresh the review queue from the stored snapshot only
```

2. **Merge after review.** The maintainer reviews `data/review/pending.md` (**start with the Star-growth alerts section**: extra analysis for repos that gained ≥100 stars in a day or leapt onto the board; if the popularity is not from the DSH plugin itself, add `leaderboard_exclusions`), records decisions in `data/approved.json` (approve) and `data/curated.json` (exclude / keep out of the board), then runs:

```bash
node scripts/merge.mjs   # regenerate CATALOG.md, TOP200.md, and the review queue
node scripts/top.mjs     # regenerate TOP200.md alone (same approval gate)
```

The raw snapshot keeps every repository under the topic (including those without a description and those on the exclusion list); filtering and approval only happen when rendering the catalog and board pages, so manual analysis always sees the complete picture. A newly created repository is younger than the stored `data/repositories.json` snapshot, so it does not appear in a `--from-snapshot` rebuild — that is expected; verify with a full `node scripts/update.mjs` run instead.

## 修改生成逻辑 / Changing the generator

改动 `scripts/` 时，请在 PR 中附带 `node scripts/merge.mjs` 重新生成的 `CATALOG.md` 和 `TOP200.md`，以便审阅者看到输出变化。

When changing `scripts/`, include the `CATALOG.md` and `TOP200.md` regenerated by `node scripts/merge.mjs` in the pull request so reviewers can see how the output changes.

## 编辑精选与订阅

`data/featured.json` 是编辑精选（顺序 + 中文推荐语）的人工维护来源：每个条目必须填写 `full_name` 和非空 `description`（按目录描述上限清洗），并在 `data/packages.json` 中有安装映射。修改文案时同步更新 `updated_at`，运行 `node scripts/validate-market-catalog.mjs` 校验投影；发布由 `publish-npm-feed` 工作流打包。自动刷新的改名同步会保留这里的引用与文案。

这份数据有两个去处：① 市场目录的 `featured` 块（客户端「精选」页签）——卡片优先采用订阅插件的身份与安装目标，文案用这里的推荐语；即使精选仓库被榜单排除（如 `tw93/Mole`、`bruc3van/bruce-md2word`），也能凭订阅插件或 AI 核对安装出现在精选里；② 官方 format-1 索引的 `featured` 标签（「编辑推荐」）——索引报告核对期望仓库数与实际打标插件数。

编辑推荐来源中的仓库数与订阅插件数分别统计：`expected_repository_count` 是推荐来源的仓库数（当前 50），一个仓库可发布多个合格插件，线上插件数可以多于仓库数。未通过来源核验（tarball 体积上限、private 包、同名重复、无安装映射等）的精选仓不会进索引，但仍在市场「精选」页签中显示（没有一键目标时走 AI 核对安装），因此索引里的 `featured` 插件数可能少于 50——这是可见的差额，不静默改动精选。更新精选时同步维护 `data/featured.json` 与安装映射，并验证市场目录、官方订阅和 npm 分发结果；只改 README 不代表推荐数据已发布。
